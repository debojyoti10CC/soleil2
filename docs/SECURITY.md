# Security and trust boundaries

Soleil is a local prototype. Its native presentation workspace executes actual **Tempo Moderato testnet** claims and transfers using free test pathUSD. The local server holds generated employer, independent caller and contractor test keys. This is **test-wallet custody**, not proof that a user controls an external wallet. A separate accounting simulation uses `sim_` references and cannot produce native receipts. No independent security audit or production readiness is claimed.

## Reviewed protections

- Passwords use asynchronous scrypt with random salts (`N=16384`, `r=8`, `p=1`). Database rows do not contain plaintext passwords. Authentication has an IP-based attempt limit.
- Random session tokens are hashed in SQLite. Cookies are HttpOnly, SameSite Strict, host-only and expire after 12 hours. Secure cookies are used when the configured application origin is HTTPS. Signing in rotates the browser's session; logout revokes it.
- Mutating requests require an allowed Origin and reject cross-site browser requests. Authenticated workspace mutations also require the session's `x-csrf-token`. Origin checking is not authentication for a non-browser client.
- Every workspace query uses the authenticated organization. Workers receive only their own contractor record, invoices and relevant activity; aggregate vault coverage remains visible. Other workers' receipts and owner-only actions are rejected server-side.
- Contractor invitations are random, stored only as hashes, expire after 72 hours, and are consumed once. Rotating an invitation invalidates its predecessor. Acceptance must use the assigned email. Soleil does not send invitation emails or verify email ownership through an email service.
- Money uses integer strings and `bigint`. Local metadata and simulation operations use atomic SQLite transactions. Native RPC/signing never runs inside an open application SQLite transaction; verified chain fields merge into the latest metadata without overwriting concurrent edits. Native transactions provide contract atomicity; an uncertain network response must be reconciled before declaring success or failure.
- Native reads verify chain ID `42431`, expected test pathUSD, executable vault bytecode/immutable configuration, employer and zero strategy, then pin balances/claims to one block. Inconsistent mappings and older blocks fail closed. Unavailable reads preserve the last verified cache, label it stale and block native writes. Native maturity uses chain block time; simulation clock/reset/strategy/restriction controls reject native workspaces.
- Commitments require `L >= P + amount + B`. Withdrawals and strategy allocations preserve `P + B`. Covered due claims remain payable below full buffer coverage; principal shortfalls block all claims. Strategy value never counts as liquid principal. Retirement releases the buffer only with zero unpaid commitments and permanently disables new commitments.
- Commitment recipients are fixed. Deterministic native payment IDs and immutable claim tuples protect retries. Receipts distinguish actual commitment and settlement hashes; a paid tuple with missing settlement indexing cannot export a fabricated payment receipt. Native financial operation keys are required, bound to the authenticated user/request and durable. Failed authorization/domain validation does not reserve a new intent; once native execution starts, uncertain or known external effects keep the key bound to its original request. Simulation/metadata keys expire after 30 days.
- Only the assigned worker can acknowledge the disclosed generated test receiving wallet; a real signature from that assigned key is verified. The local server holds that key, so acknowledgement does not establish user custody or validate an external address. External receiving addresses are rejected until an external-wallet signing workflow exists.

These controls protect the declared workflow. They do not establish token value, legal ownership, bankruptcy priority, bank delivery, guaranteed network availability, or immunity from defects. Token policy and contract execution remain authoritative if conditions change after a displayed read.

## Local application and testnet relay

Keep the server and Vite bound to loopback. `SOLEIL_NATIVE_ENABLED=true` explicitly enables the persistent native adapter. Demo access separately requires `SOLEIL_DEMO_ENABLED=true` (or `ALLOW_DEMO=true`). Prepared presentation and demo sign-in provide local convenience access to shared test identities; they are not public production authentication. Native wallet/provisioning endpoints require both a loopback socket and loopback application origin; a public reverse proxy origin is refused. Normal registration creates an empty native company until its owner explicitly provisions it.

The native keystore generates isolated keys and encrypts wallet files with AES-GCM bound to their scope. On Windows, DPAPI protects the encryption master for the current OS user; elsewhere it is a permission-restricted key file. There is no user-key import/export API. Keys, encrypted wallets and the signed transaction journal live in ignored `data/`; protect and preserve them across restarts. Local user/machine compromise can defeat these boundaries. Unix mode bits are not a replacement for reviewing Windows directory ACLs.

Before broadcast, the adapter durably saves exact signed bytes and their hash. Wallet locks serialize signing; refresh/retry/restart reconciles saved bytes by hash rather than silently signing a replacement. `NATIVE_PENDING`/`NATIVE_OUTCOME_UNKNOWN` means preserve journal files, refresh, and retry the same operation key. A timeout does not prove failure: the transaction may already have executed. A confirmed revert or pre-sign rejection is shown separately. Ordinary presentation login and commit/pay do not request faucet funds or deploy a contract; preparation/provisioning explicitly performs those setup steps. Recovery is tested for this prototype, not guaranteed for arbitrary failures or production chain reorganization.

`POST /api/testnet/rpc` is available only with explicit native or demo configuration. It forwards to the fixed `https://rpc.moderato.tempo.xyz` URL, accepts an enumerated method list, and rejects caller-supplied upstream URLs and JSON-RPC batches. Reads support the logged-out independent verifier. Faucet and signed-transaction writes additionally require both a loopback connection and a loopback browser origin; a public reverse proxy origin is not accepted as local.

The relay has a 64 KB request limit, a 2 MB response limit, an upstream deadline, concurrency limits and separate read/write rate limits. It accepts signed bytes, but no private keys, and emits bounded errors. The separate browser lab creates temporary isolated keys in browser memory, distinct from persistent presentation keys, and checks chain ID `42431` and the expected test asset before funding/deployment. Refreshing can lose browser-lab keys; use free test assets only.

The independent verifier checks the vault runtime against the compiled artifact, accounts for immutable constructor slots, and reads the actual token, strategy, beneficiary and claim state. Nominal balance coverage is distinct from current token transfer eligibility and network availability. Contract execution remains authoritative if a displayed read becomes stale. See [CHAIN-CONTRACTS.md](CHAIN-CONTRACTS.md).

## Provider and data boundaries

Formation is an external Stablecorp or Stripe Atlas handoff. A handoff cannot mark formation, KYB, banking or payment routes approved. Bridge configuration placeholders are not a working provider integration or commercial approval. Testnet money operations do not call a bank or deliver fiat cashout. The presentation vault has no strategy and reports no simulated yield.

Business names, contractor contact details and invoice descriptions are private API data stored in the local SQLite file. The application database is **not encrypted at rest**; the signed transaction journal is also a private local operational file. Protect filesystem permissions and backups. Do not enter passports, tax documents, bank credentials, production wallet keys or sensitive provider-verification documents. Native addresses, claim amounts and transaction hashes are public chain data. Public evidence/configuration contains no key material and is not proof of current liveness. Workflow CSV is not a comprehensive chain or bank ledger.

## Before production use

Mainnet/real-money use requires independently reviewed contracts and deployment/signing authorities; verified supported asset/account semantics; a real wallet/custody and consent model; durable indexing/finality/recovery; tested backups/restoration; production authentication, abuse controls, monitoring and incident handling; encryption/retention/access policies; and narrowly scoped sponsorship. The current native executor is deliberately fixed to free testnet assets and generated test wallets.

Live fiat or formation services additionally require provider contracts, approved customer/country/asset routes, consent, fee disclosure, signed-webhook reconciliation and failed-transfer/refund handling. Legal review must assess the actual keys, custody, transfer authority, fees and jurisdictions. Mainnet funds require those gates and independent security review, not merely passing demo tests or matching a compiled binary.
